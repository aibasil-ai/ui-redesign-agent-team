## 1. 文件目的

在 OpenCode 中建立一組專門處理「UI 設計素材 → 既有前端專案還原實作」的 Agent 團隊（6 個），
與現有的協調者／開發者／審核者三人組**完全獨立並存**：三人組繼續負責一般功能開發，完全不動；
新團隊專責 UI 重構，且設計為**可搬走的套件**，未來可直接複製到其他前端專案使用。

## 2. 目標與成功標準

1. **設計還原度**：新 UI 盡可能貼近設計素材（版面、尺寸、間距、字體、顏色、元件樣式）。
2. **功能完整性**：既有功能、事件、API 契約、資料流、操作邏輯一律保留，不因 UI 改版被破壞。
3. **持續開發能力**：改版完成後，既有三人組可繼續在同一程式碼上開發功能。
4. **可攜性**：新團隊的 6 個 agent 本體不包含任何專案特定資訊；搬家 = 複製資料夾＋依 §5.3 安裝必改清單調整＋填一份專案設定檔。

## 3. 團隊架構總覽

共 9 個 agent：現有 3 個不動，新增 6 個（含 UI 專屬協調者）。

| Agent ID | 模式 | 核心職責 | 修改權限 |
|---|---|---|---|
| `orchestrator`（既有） | primary | 一般功能開發的協調迴圈 | 不動，維持現狀 |
| `developer`（既有） | subagent | 一般功能實作 | 不動，維持現狀 |
| `reviewer`（既有） | all | 一般功能開發的程式審核 | 不動，維持現狀 |
| `ui-redesign/orchestrator` | primary | UI 重構七階段流程協調、派工、輪數控制、dev server 管理、交付 | 不改程式；僅可寫 `.opencode/ui-redesign-kit/ui-profile.md`（僅主工作區路徑，不經 worktree 路徑） |
| `ui-redesign/design-analyzer` | subagent | 解析設計素材 → 設計規格、design tokens、元件對照、待確認清單 | 唯讀程式碼；僅可寫自己的四份產物檔 |
| `ui-redesign/developer` | subagent | 依設計規格實作 UI，優先重用既有元件與邏輯 | 可改產品程式碼（禁 `.opencode/**`、`.env*`、worktree 前綴同罪） |
| `ui-redesign/visual-qa` | subagent | 截圖比對設計素材 → 視覺差異報告 | 唯讀程式碼；僅可寫視覺報告與 `.artifacts/` |
| `ui-redesign/functional-qa` | subagent | 建立功能基準（含特徵測試、回歸腳本）＋改版後功能回歸 | 唯讀程式碼；可寫自己的兩份產物、`scripts/`；測試檔走 ask |
| `ui-redesign/reviewer` | subagent | 程式品質、樣式污染、相容性、XSS/安全、非預期改動 | 唯讀程式碼；唯一寫入例外：自己的 `code-review.md` |

職責分離原則：**實作與視覺判定分離**（developer 不自行宣告還原正確）；**功能回歸與程式審核兩條線分開**；
所有審核以證據（截圖、量測值、測試結果、diff）為依據，不得以主觀描述代替。
**分工由權限強制**：所有 agent 的 `subagent` 權限一律**先 `deny *`**；唯一能派工的是 orchestrator，
且僅限 5 個 `ui-redesign/` 完整 ID 例外（§11）——任何 agent 無法再派工繞過分工。

## 4. 檔案結構與命名

命名定案：kit 資料夾 `ui-redesign-kit`，agent 前綴 `ui-redesign/`（ID 來自子資料夾路徑，OpenCode V2 支援）。

```
.opencode/
├── agents/
│   ├── orchestrator.md、developer.md、reviewer.md   ← 既有 3 個，完全不動
│   └── ui-redesign/                                 ← ★ 新增（搬專案 = 複製這個）
│       ├── orchestrator.md          ID: ui-redesign/orchestrator（primary）
│       ├── design-analyzer.md       ID: ui-redesign/design-analyzer
│       ├── developer.md             ID: ui-redesign/developer
│       ├── visual-qa.md             ID: ui-redesign/visual-qa
│       ├── functional-qa.md         ID: ui-redesign/functional-qa
│       └── reviewer.md              ID: ui-redesign/reviewer
└── ui-redesign-kit/                                 ← ★ kit 專用資料夾（跟著一起搬）
    ├── ui-profile.md            每專案設定檔（kit 內唯一專案特定內容）
    ├── ui-profile-範本.md        ui-profile.md 的範本（搬到新專案後複製成上者並填寫）
    ├── 安裝指南.md               搬家與初始化的標準程序（含 §5.3 安裝必改清單）
    ├── commands/ui-redesign.md  /ui-redesign 命令檔（安裝時複製到 .opencode/commands/）
    └── tools/                   瀏覽器工具包（獨立 package.json，用「工具用 Node」執行）
        ├── package.json         依賴：playwright、pixelmatch、pngjs
        ├── shot.cmd / shot.mjs  截圖＋頁內量測工具
        ├── diff.cmd / diff.mjs  兩圖比對（內建對齊、overlay、diff、差異百分比 JSON）
        ├── run.cmd / run.mjs    執行 <產物根目錄>/<slug>/scripts/ 內的客製腳本（路徑驗證）
        ├── codegen.cmd          Playwright codegen 錄製包裝（可選輔助）
        ├── .tool-node.cmd       工具用 Node 絕對路徑（安裝時產生；gitignore，見 §6.1）
        └── setup.cmd            初始化包裝（npm install＋playwright install＋產生 .tool-node.cmd）
```

agent 檔案格式：OpenCode V2 markdown agent。frontmatter 使用 `description`、`mode`、`model`（**完整格式 `provider/model#variant`**）、`permissions`。
**權限動作名使用 V2 名稱：`edit`、`shell`、`subagent`、`webfetch`、`websearch`**（不是 V1 的 `bash`/`task`）。
注意：既有 3 個 agent 使用的 `permission:` 單數 map 為 V1 舊格式（仍可運作但已 deprecated，model 與 variant 分開欄位）；新團隊一律用 V2 格式，**不回頭改既有檔案**。

**現況限制（本專案）**：`.gitignore` 已忽略 `/docs/` 與 `.opencode/`（既有規則，不動）。本專案的 kit／agent 檔案僅存本機（搬家從本機複製）；產物的版控問題見 §9 決策 D1。

## 5. 可攜性設計

### 5.1 零專案資訊原則與衝突原則

6 個 agent 本體不寫死任何專案資訊（技術棧、路徑、指令、基準線數字一律不寫進 agent）。
每個 agent 開工第一步：讀取 `.opencode/ui-redesign-kit/ui-profile.md`。

- 檔案存在 → 依其內容工作。
- 檔案不存在 → 停止並回報 `ui-redesign/orchestrator`；orchestrator 以 `ui-profile-範本.md` 為提綱，
  用 `question` 向使用者蒐集必要欄位 → 產生檔案 → **請使用者確認後**才開始正式流程。

**權限樣式中的可替換標記**：§11 的權限規則使用 `<產物根目錄>`（依 ui-profile 決策 D1 落地時字串替換）
與 `.worktrees/**`（本套件的隔離區約定目錄名）。這是「安裝時設定」而非「agent 本體寫死專案資訊」，見 §5.3。

**與專案 instructions 的衝突原則**：專案 instructions（如本專案注入的 `workflow-rules.md`）會自動進入所有
agent 上下文。每個 `ui-redesign/` subagent 正文必須聲明：「你的工作由 `ui-redesign/orchestrator` 協調——
worktree 建立/清除、commit、合併一律由 orchestrator 負責，你**不執行也不詢問**使用者 worktree／commit 事項；
與注入的專案規則衝突時，以本指令的職責劃分為準。」

### 5.2 ui-profile.md 欄位規格

| 區塊 | 欄位 |
|---|---|
| 專案基本 | 專案名稱、技術棧、專案用 Node 版本、**工具用 Node 絕對路徑**（執行 kit tools 的 node.exe，與專案 Node 版本無關） |
| 指令 | dev server（啟動指令、port、就緒判斷方式）、test／lint／build 指令與 timeout、測試基準線（項數）、測試慣例（框架、**測試目錄**、寫法參考檔） |
| 樣式系統 | 樣式機制（less/scss/css 變數/Vuetify theme…）、design tokens 映射位置、全域樣式檔、禁改樣式區 |
| 結構 | 頁面目錄、元件目錄、store、API 層、i18n 檔、路由檔 |
| 頁面進入前置 | 目標頁進入所需條件與**取得方式**：無認證（直接開 URL）或需認證/前置（提供 **storageState 檔案路徑**或 cookie/token 來源檔；shot 以 `--url-file` 內的 `storageState` 欄位帶入，functional-qa 客製腳本比照讀取同一欄位）。**憑證不得寫進 ui-profile 明文、產物、log**；storageState 檔放 gitignored 路徑，由使用者提供 |
| 安全不變量 | 專案的渲染安全慣例（如外部資料渲染前須經 sanitizer）、既有 `v-html` 位置與契約——reviewer 與 developer 必讀 |
| 禁改區 | 預設：API 契約、store 核心狀態、socket 事件、路由資料流（可依專案增補；可選強化：把路徑加進 developer 的 edit deny，見 §5.4） |
| 設計素材 | PNG/JPEG、HTML 原型（檔案路徑或網址）、規格/標注文件的路徑清單與說明 |
| 驗收 | Viewport 清單、差異像素門檻（試行 2%，可調）、特別驗收要求 |
| 產物 | **產物根目錄**（預設 `docs/ui-redesign/`，可依專案版控情況改變，見 §9 決策 D1） |
| 流程程序文件 | （可選）指向專案的 worktree／流程程序文件；未填時 orchestrator **依套件內建 `.opencode/ui-redesign-kit/worktree-procedures.md`** 執行（§8.5 情境二已物質化為套件檔案）。**引用任何程序時，§8.5 情境一的套件插入規則一律適用** |
| 其他 | eslint 風格、語系、commit 規範引用 |

### 5.3 安裝必改清單（`安裝指南.md` 核心）

搬專案後**必做**（agent 本體仍零專案資訊，這些是安裝時的套件設定）：

1. 複製 `.opencode/agents/ui-redesign/` 與 `.opencode/ui-redesign-kit/` 到新專案。
2. 依 `ui-profile-範本.md` 填 `.opencode/ui-redesign-kit/ui-profile.md`（含工具用 Node 絕對路徑）。
3. **`<產物根目錄>` 字串替換**：若產物根目錄非預設 `docs/ui-redesign`，把 6 個 agent 檔案權限規則中的
   `<產物根目錄>` 一併替換（`run.cmd` 由工具讀 ui-profile 動態解析，不需替換）。
4. **測試目錄 ask 路徑**：`ui-redesign/functional-qa.md` 中 `test/**`（含 worktree 前綴那條）依專案實際
   測試目錄調整——兩條一起改（§11 functional-qa）。
5. **隔離區目錄名**：套件約定 `.worktrees/`；若專案沿用不同名稱，除權限樣式中的 `.worktrees/**` 外，
   **工具路徑契約（§6.2 的 `.worktrees` 前綴判定式）也要同步**（建議直接沿用，免改）。
6. **test／lint／build 的 shell allow 字串**：§11 中 `npm test*`／`npm run build*`／`npm run lint*`／
   `npx eslint*` 是 npm 生態預設；非 npm 專案（或指令不同的專案）改為 ui-profile 對應指令的字串規則
   （涉及 orchestrator、functional-qa、reviewer 三個檔案）。
7. 工具初始化：執行 `tools/setup.cmd`（互動式：①讀 ui-profile 取工具用 Node 路徑並產生 `.tool-node.cmd`
   ②**詢問 Chromium 安裝位置**——[1] 使用者快取共用（Playwright 預設，`%LOCALAPPDATA%\ms-playwright`，
   約 150MB 本機所有專案共用）或 [2] 專案內隔離（`tools/.browsers/`，約 300MB，gitignore 排除，
   每個專案重新下載）；選 [2] 時一併把 `PLAYWRIGHT_BROWSERS_PATH` 寫進 `.tool-node.cmd`，
   工具執行期自動生效——③以工具用 Node 執行 `npm install` ④`npx playwright install chromium`
   （位置依②的選擇））。
8. **`.tool-node.cmd` 加入專案 .gitignore**（機器特定內容）。
9. 自我驗證：跑一次 shot（測試頁截圖）＋一次 diff（兩圖比對）確認工具鏈通。
10. （可選）複製 `commands/ui-redesign.md` 到 `.opencode/commands/`。
11. 依專案情況設定產物版控（§9 決策 D1）與 `.artifacts/` 的 gitignore 行。
12. 開啟 OpenCode 確認 6 個 `ui-redesign/` agent 都可見。

### 5.4 每專案微調點（原則：能不改就不改）

| 項目 | 預設 | 類型 |
|---|---|---|
| `<產物根目錄>` 權限樣式 | `docs/ui-redesign` | 安裝必改（非預設值時） |
| functional-qa 測試檔 ask 路徑（雙前綴兩條一起改） | `test/**` ＋ `.worktrees/**/test/**` | 安裝必改（目錄名不同時） |
| test／lint／build 的 shell allow 字串（orchestrator、functional-qa、reviewer） | `npm …` | 安裝必改（非 npm 生態時） |
| 隔離區目錄名 `.worktrees/**` | `.worktrees/` | 安裝必改（沿用不同名稱時） |
| `.tool-node.cmd` 的 gitignore 行 | 有 | 安裝必改 |
| developer 的 edit deny 禁改區路徑 | 無（禁改區僅指令層級規範） | 可選（經使用者同意加入，讓權限強制） |

## 6. 工具鏈設計

### 6.1 決策摘要

- **不使用 Playwright MCP**。採「**通用工具為主、必要時客製腳本**」：kit 提供固定的 shot／diff 工具，
  agent 以參數呼叫；互動流程由 functional-qa 撰寫客製 Playwright 腳本（經 `run.cmd` 執行）。
  理由：視覺迴圈的本質是「固定條件截圖 → 比對 → 修正 → 重截圖」，同一工具/腳本重跑＝條件完全一致，重現性優於 MCP 的逐步互動。
- **瀏覽器用 Playwright 自帶 Chromium**，不用系統 Chrome——與使用者日常環境（含登入狀態）完全隔離。
  需要登入態的頁面以 `--url-file` 內的 `storageState` 欄位帶入使用者提供的 session 檔（§5.2、§6.2），憑證不落地到 kit/產物。
  **瀏覽器安裝位置由 setup.cmd 安裝時詢問**：[1] 使用者快取共用（Playwright 預設）或 [2] 專案內隔離
  （`tools/.browsers/`，經 `.tool-node.cmd` 的 `PLAYWRIGHT_BROWSERS_PATH` 生效）；差異與取捨見 §5.3 第 7 項。
- **工具用 Node 與專案 Node 分離**：kit tools 一律以「工具用 Node」執行（本機為 nvm 的 v24.15.0），
  不切換全域預設版本、不碰專案 package.json。
- **Node 路徑橋接（.tool-node.cmd）**：agent 的 shell 白名單不能含機器特定絕對路徑。
  安裝時由 `setup.cmd`（或手動）產生 `tools/.tool-node.cmd`（一行：`set "TOOL_NODE=<工具用 Node 絕對路徑>"`，
  值依 ui-profile）。所有工具 `.cmd` 開頭 `call "%~dp0.tool-node.cmd"` 後以 `%TOOL_NODE%` 執行對應 `.mjs`。
  `.tool-node.cmd` 加入 gitignore；ui-profile 的路徑欄位仍是給人核對的來源。
- **工具呼叫格式（agent 正文逐字規定）**：`cmd /c .opencode\ui-redesign-kit\tools\<工具>.cmd <參數>`
  （反斜線）；**必須單獨執行，不得與其他指令串接**（`&&`、`;`、`|`、`&`、換行續行一律視為違規；
  權限層對 `&&`、`;`、`|`、`&` 有 deny 強化，見 §11）。
- **URL 參數傳遞契約（A2 決策）**：所有工具**不直接接收**含 `&`、`;`、`|` 等 shell 串接風險字元的 URL。
  呼叫者先把網址寫入 gitignored 的參數檔（預設放目標頁 `.artifacts/` 下，例如 `<slug>/.artifacts/url-args.json`，
  內容為單一 JSON：`{"url":"https://..."}`，可選帶 `storageState` 等），再以 `--url-file <參數檔路徑>`
  傳給工具；工具只接收檔案路徑，讀取後解析 URL。此設計同時滿足：①shell 白名單可維持串接 deny
  ②URL 查詢字串不需編碼 ③參數檔受 §6.2 輸出路徑契約保護。

### 6.2 工具規格（CLI 契約）

**主工作區根推導（唯一演算法）**：`.tool-node.cmd` 所在目錄為 `<專案根>/.opencode/ui-redesign-kit/tools/`。
  以該檔案 realpath 解析後的所在目錄為起點，向上取三層父目錄即為專案根：

```js
// 位於 .../tools/.tool-node.cmd
const toolsDir = fs.realpathSync(path.dirname(fileURLToPath(import.meta.url)));  // .../tools/
const kitDir = path.resolve(toolsDir, '..');                                      // .../ui-redesign-kit/
const opencodeDir = path.resolve(kitDir, '..');                                   // .../.opencode/
const projectRoot = path.resolve(opencodeDir, '..');                              // 專案根
```

**路徑驗證契約**（適用範圍明確劃分）：

- **適用：輸出路徑**——shot/diff 的 `--out`、run 的腳本路徑。realpath 解析後必須落在下列允許集合
  （逐一前綴比對，命中即放行；前綴比對以**區段邊界**為準，避免 `docs/ui-redesign` 誤匹配
  `docs/ui-redesign-something`）：
  - `<專案根>\<產物根目錄>\<slug>\…`（輸出限 `.artifacts/` 子樹；run 限 `scripts/` 子樹）
  - `<專案根>\.worktrees\<任何名稱>\<產物根目錄>\<slug>\…`（同上子樹限制）
  - 拒絕條件：realpath 後落在集合之外、含 `..` 跳脫、符號連結脫離該集合。
- **不適用：輸入路徑**——`--design`、`--actual`、本地 HTML 原型、`--storage-state`、`--url-file` 等**唯讀輸入**
  不套用產物集合（設計素材、storageState、URL 參數檔本來就在產物樹外）；契約為「**工具對輸入路徑僅讀取**，
  除 `--out` 外不寫入任何位置」＋同樣拒絕 `..` 跳脫。

所有工具：結束碼 `0`=成功、非 `0`=失敗；錯誤訊息輸出到 stderr；`--help` 顯示用法。

| 工具 | 參數 | 輸出 | 使用者 |
|---|---|---|---|
| `shot`（截圖模式） | `--url-file <參數檔路徑>`（內含 `url`、`storageState` 等）、`--viewport <WxH>`、`--wait <網路idle/選擇器>`、`--full-page`、`--scale <deviceScaleFactor>`、`--out <路徑>` | PNG 截圖 | visual-qa |
| `shot`（量測模式） | `--url-file <參數檔路徑>`、`--measure <選擇器範圍或 all>`、`--out` | 頁內量測 JSON（getBoundingClientRect、getComputedStyle：座標、寬高、間距、字級、顏色） | design-analyzer |
| `diff` | `--design <設計圖>`、`--actual <實際截圖>`、`--align width|exact`（內建縮放對齊：以設計圖寬度為基準縮放實際截圖；高度不足補白、過長裁切並在結果標註高度差異）、`--threshold`、`--out` | overlay 圖、diff 圖、差異像素百分比 JSON（含對齊後尺寸資訊） | visual-qa |
| `run` | `<腳本.mjs> [參數]`——腳本路徑依輸出契約驗證（僅限 `<產物根目錄>/<slug>/scripts/` 子樹，接受 worktree 內對應路徑），以工具用 Node 執行 | 腳本輸出／結束碼 | functional-qa |
| `codegen` | `--url-file <參數檔路徑>` | 開瀏覽器供使用者手動操作，產生腳本程式碼（**可選輔助**，非標準流程） | functional-qa（需要時） |

**已知邊界（§15 同步記錄）**：客製腳本以工具用 Node 執行＝具備完整 Node 能力（可寫檔）。防護三層：
①工具端路徑驗證（僅 `scripts/` 子樹）②functional-qa 正文規定「**首次執行任一腳本前，於回覆中列出路徑與用途**」
③安裝指南向使用者說明此邊界。

### 6.3 瀏覽器資源約束

Chromium 為單一資源：**所有使用瀏覽器的工作（design-analyzer 的量測、visual-qa 的截圖、functional-qa 的
操作）由 `ui-redesign/orchestrator` 序列化**，不並行，錯開排程。

### 6.4 dev server 管理（ui-redesign/orchestrator 職責）

- 階段 0 以背景 bash 啟動（依 ui-profile 的指令），啟動前檢查 port 占用：
  - 未占用 → 由 orchestrator 啟動並**標記為本任務所有**。
  - 已占用（使用者手動開啟）→ 詢問沿用或由 orchestrator 另開 port；**沿用時標記「非本任務所有」，收尾一律不終止它**。
- **工作目錄**：有 worktree 時，dev server 的 bash 以**該 worktree 絕對路徑**為 `workdir`（不得在主工作區啟動，否則截圖與測試會對到舊程式）。
- 就緒判斷（依 ui-profile 欄位）通過後將 URL 傳給各 QA。
- **啟動失敗 → 停止流程並回報使用者**，不擅自跳過或改用其他方式。
- 關閉時機：正常交付完成、使用者決定中止、任何異常收尾——僅終止「本任務所有」的程序（以監聽 port 找 PID，
  如 `Get-NetTCPConnection` → `Stop-Process`），並回報「dev server 已停止／沿用的 dev server 保留未動」。
  列入收尾檢查清單（§8.4）。

## 7. 流程編排（ui-redesign/orchestrator）

### 7.1 七階段主流程

```
階段 0 準備      讀 ui-profile（無→範本蒐集產生並經使用者確認）→ 確認設計素材與目標頁
                → 詢問 worktree（依 ui-profile「流程程序文件」；未填則 §8.5 情境二）→ 啟動 dev server
階段 1 基準建立  （以背景派工並行；瀏覽器工作錯開；環境不支援背景派工則序列化）
                ui-redesign/functional-qa：盤點既有功能 → 補特徵測試（舊版先通過）→
                寫回歸腳本 → 跑全部既有測試記基準線 → functional-baseline.md
                ui-redesign/design-analyzer：解析素材 → design-spec.md、design-tokens.json、
                component-mapping.md、pending-questions.md
階段 1.5 決策點  orchestrator 把待確認清單用 question 問使用者 → 決策**由 design-analyzer（重派，
                帶決策內容）回寫** pending-questions.md 並修訂 design-spec.md／design-tokens.json
                → **使用者確認 design-spec 與 design-tokens 兩者** → 凍結，進入實作
階段 2 實作      ui-redesign/developer 分批：先 tokens／共用元件 → 頁面分區
階段 3 視覺迴圈  ui-redesign/visual-qa 截圖比對 → FAIL 退 developer 只修指定項 → 重比對（見 §8.1/8.2）
階段 4 驗收      兩條線**序列化**執行（test/build 不並行，避免互搶 .nuxt 與測試鎖；瀏覽器亦錯開）：
                先 ui-redesign/functional-qa（重跑回歸腳本＋全部測試＋build → functional-report.md），
                後 ui-redesign/reviewer（lint＋自己的 test/build 驗證＋程式審核 → code-review.md）
                任一 FAIL → 指定範圍退回 developer → 重跑對應驗收（見 §8.1）
階段 5 交付      彙整三份報告＋建議手動回歸清單 → 擬繁中 commit 訊息給使用者審核（含產物文件）→
                同意才 commit → dev server 關閉 → worktree 合併/清除程序 → 絕不 push
```

### 7.2 ui-redesign/functional-qa 的兩次登場

- **階段 1（baseline 模式）**：先織網——功能盤點、特徵測試（鎖定現行行為，在未修改的舊程式上先通過）、
  回歸腳本（關鍵操作流程，舊版跑通過並記錄結果）、全部測試基準線。順序**不可顛倒**：若先改版再盤點，舊行為已消失，防護網織不出來。
- **階段 4（regression 模式）**：重跑同一批回歸腳本＋全部測試＋build，與基準線比對（項數不得少於、不得有失敗）。

無測試保護的既有功能分三類處理：可測試邏輯→補特徵測試；關鍵操作流程→回歸腳本；自動化不了→列入建議手動回歸清單。

### 7.3 派工規則

- **subagent 白名單**只允許呼叫 5 個 `ui-redesign/` subagent（**完整 agent ID**，如 `ui-redesign/developer`）；
  每次呼叫必帶：工作目錄絕對路徑、本次任務、相關產物文件路徑。分工由權限強制（§3、§11）。
- **session 延續規則**：developer 每輪呼叫帶回其 child session 的 `sessionID`（子代理工作階段識別碼，
  延續同一 session；實作時依官方文件核對欄位名，見 §17）；所有審核/QA 角色**每輪派新的**
  （不帶舊 sessionID，確保獨立性）。
- 階段 1 並行：兩個 subagent 以**背景派工**啟動（子代理背景模式），瀏覽器工作由 orchestrator 錯開；
  環境不支援背景派工時改為序列化執行。
- **有 worktree 時的工作目錄規則（白名單式，三處同文）**：
  - **用 worktree 絕對路徑為 `workdir`**：工作期間的操作——test/lint/build、dev server、產物與測試檔讀寫、
    developer 的程式編輯、QA 的瀏覽器工作、**git add／git commit／交付與清除前的 git status**
    （該分支只 checkout 在 worktree，必須在 worktree 內提交）。
  - **一律在主工作區根目錄執行（例外清單）**：worktree 建立（`git worktree add`）、
    **worktree 清除全程**（兩個 junction 的 `cmd /c rmdir` 與 `git worktree remove`——相對路徑設計，
    在 worktree 內執行會找不到路徑）、`git merge`（合併對象是主工作區分支，含合併前在主工作區查看分支狀態）。
  - **session 工作根原則（A1 決策）**：subagent 呼叫時傳入該 worktree 絕對路徑作為 `workdir`；依 OpenCode
    行為，此舉預期會使該 subagent 的 session 工作根落在 worktree 內，從而使「edit 一律使用相對路徑」生效。
    若 §17 實測發現 OpenCode 不會把 session 工作根移到 worktree，則回退為方案②：session 留在主工作區、
    edit 路徑強制以 `.worktrees/ui-<slug>/` 開頭；此時 §11 的雙前綴樣式即為該 fallback 所需。

## 8. 迴圈、邊界與異常處理

### 8.1 輪數定義（統一）

- **1 輪 = 一次 developer 修正 ＋ 該迴圈的重驗**。首次執行（開發＋首次審核）算第 1 輪。
- **視覺迴圈（階段 3）**與**驗收（階段 4）各自有獨立的 3 輪預算**，分開計數。
- 階段 4 的兩條驗收線在同一輪內**序列化**執行（§7.1），各自回報，不雙計輪數。
- **快速視覺比對**（§8.3 的防回歸加跑）**不計輪**。
- 第 3 輪仍 FAIL → 停止自動迴圈；使用者同意後**每次只追加 1 輪**，追加輪後仍 FAIL 再次詢問，不自動續跑。

### 8.2 視覺迴圈第 3 輪仍 FAIL 的處理

orchestrator 以 question 提供四選項（附該輪 overlay／diff 圖路徑與 visual-report）：

1. **再修一輪**：追加 1 輪（developer 修正 → visual-qa 重比對）。
2. **使用者裁決差異可接受** → 帶未解項進階段 4（未解項記入 visual-report「剩餘限制」與最終驗收總結，不會消失）。
3. **使用者自己手動調整**：保留現狀，之後重跑視覺比對確認。
4. **暫停任務**：說明 worktree 位置與分支，下次再續。

**不得未經使用者裁決直接帶失敗狀態進階段 4。**

### 8.3 嚴重度與防回歸

- **嚴重度三級**（嚴重／一般／建議）：只有「嚴重或一般」問題才 FAIL；「建議」級不擋 PASS。
- **同題連修 3 次無改善 → 提前停止**：重新分析原因（如要求 design-analyzer 重新量測、判斷是否推估錯誤），不盲目重試。
- **跨階段防回歸**：階段 4 退回 developer 修正後，若異動含樣式/template 類檔案，orchestrator **加跑一次快速視覺比對**（驗證已通過區域未被打壞）才重跑功能回歸。
- **驗收門檻**：差異像素百分比為**參考門檻**（試行值 <2%，記於 ui-profile 可調）；**最終驗收由使用者**看完 overlay／diff 圖與 visual-report 後裁決。不得宣稱「達成 98% 還原度」之類的數字話術。

### 8.4 異常處理表

| 異常 | 處理 |
|---|---|
| ui-profile 不存在 | orchestrator 用範本蒐集產生 → 使用者確認後才開工 |
| dev server 啟動失敗 | 停止並回報使用者；由使用者決定重試或中止 |
| 沿用的 dev server（非本任務啟動） | 收尾**一律不終止**；結束時回報「沿用的 dev server 保留未動」 |
| 設計素材缺失／格式不符 | design-analyzer 回報清單 → orchestrator 用 question 請使用者補件或裁決；不推測、不虛構 |
| 工具用 Node 路徑失效（.tool-node.cmd 執行失敗） | 停止並回報；依安裝指南重新產生；不自行改用其他 Node |
| shot/diff/run 執行失敗 | 如實回報 stderr 與結束碼；同一工具連續失敗 3 次停止並回報使用者 |
| worktree 同名目錄或分支已存在 | 不硬蓋：停下用 `question` 請使用者決定（換名稱或先處理殘留） |
| worktree 建立/清除失敗 | 依 ui-profile「流程程序文件」＋§8.5 情境一的插入規則處理；未填則 §8.5 情境二；失敗如實回報殘留狀況 |
| **清除時 kit junction 的 rmdir 失敗** | **中止清除並回報**（連結未拆則 `worktree remove` 可能跟隨刪除主工作區 kit）。判準：若路徑本來不存在 → 視為已拆除；若存在但 `rmdir` 失敗 → 中止。node_modules 的 rmdir 失敗（實體目錄或不存在路徑）可忽略 |
| functional-qa 的 ask 被使用者拒絕 | **停止該項工作並回報**，不可自行改道；該功能改列「建議手動回歸檢查」 |
| 需登入的頁面無法取得 storageState | 視覺／功能驗證受限：如實標註於報告，能驗的部分先驗，其餘列「建議手動回歸檢查」 |
| **收尾檢查（一律）** | ①dev server 已關（沿用的除外）②worktree 已清除或已告知殘留 ③**產物文件已 commit，或未 commit 時經使用者明確同意丟棄後才可 `worktree remove --force`（否則不得清除）** ④三份報告與剩餘限制已向使用者彙整 |

### 8.5 worktree 程序

#### 情境一：ui-profile 填了「流程程序文件」（本專案：`.opencode/worktree-procedures.md`）

以該程序為**主體**執行建立與清除，但一律遵守四條套件插入規則：

1. **worktree 目錄與分支命名**：
   - 目錄名依程序的 `<類型>-<slug>` 模式，UI 任務固定 **`<類型> = ui`**：`.worktrees/ui-<slug>`。
   - **分支名刻意不同於目錄**：`ui-redesign/<slug>`（避免與 feature/bugfix 等既有分支混淆）。
   - 完整建立指令：
     ```powershell
     git worktree add .worktrees/ui-<slug> -b ui-redesign/<slug> [起點]
     ```
   - §11 的 `.worktrees/**/…` 雙前綴樣式只要求在 `.worktrees/` 之下，不限名稱，天然相容。
2. **kit junction 插入點（建立）**：在該程序「worktree 目錄建立完成之後、依賴處理之前」插入：
   ```powershell
   New-Item -ItemType Directory -Path .worktrees/ui-<slug>/.opencode -Force
   New-Item -ItemType Junction -Path .worktrees/ui-<slug>/.opencode/ui-redesign-kit -Target <主工作區絕對路徑>\.opencode\ui-redesign-kit
   Test-Path .worktrees/ui-<slug>/.opencode/ui-redesign-kit/ui-profile.md   # 必須為 True，否則停止並回報
   ```
   （讓 worktree 內讀得到 ui-profile、執得到 tools——§11 的相對路徑白名單與雙前綴樣式據此成立。）
3. **kit junction 拆除插入點（清除）**：在該程序清除流程中、**`git worktree remove` 之前**插入
   `cmd /c rmdir .worktrees\ui-<slug>\.opencode\ui-redesign-kit`，與 node_modules 的拆除同批先執行；
   **嚴禁排在 `git worktree remove` 之後**。
4. **清除閘門**：執行 `git worktree remove` 之前——
   ① **產物文件已 commit，或未 commit 時經使用者明確同意丟棄**（--force 會刪除未追蹤檔）。
      具體確認：先在 worktree 內執行 `git status --short` 檢查未追蹤產物與未 stage 變更，回報使用者。
   ② **kit junction 的 rmdir 已成功**——失敗即**中止清除並回報**，不可繼續。
      判準：若路徑本來不存在 → 視為已拆除；若存在但 rmdir 失敗 → 中止。
   ③ node_modules 的 rmdir 失敗（實體目錄或不存在的路徑）可忽略。

> **警告（與 node_modules 同等級）**：kit junction 若被 `git worktree remove --force` 跟隨刪除，
> 會把主工作區的 `.opencode/ui-redesign-kit`（agent、tools、ui-profile）**整包刪除**；
> 該目錄被 `.gitignore` 忽略（`.opencode/`），**無法從版控還原**。拆除 kit junction 的步驟不可省略、不可後置。

#### 情境二：ui-profile 未填「流程程序文件」→ 完整通用程序

> **v7 註記**：情境二已**物質化**為套件內建檔案 `.opencode/ui-redesign-kit/worktree-procedures.md`——執行時 orchestrator 讀取該檔逐條執行（使用者可直接修改該檔微調程序）；檔案缺失＝套件安裝不完整，停止並回報。以下內文為該檔的規格依據。

**建立**（以下指令除特別標註外，皆在主工作區根目錄執行）：

1. `git rev-parse HEAD` 取得起點 sha，記為**比較基準**。
2. 由任務產生英文小寫連字號 `<slug>`；**先檢查殘留**：`Test-Path .worktrees/ui-<slug>` 與
   `git branch --list ui-redesign/<slug>`——已存在時**不硬蓋**，用 `question` 請使用者決定（換名或處理殘留）。
3. `git worktree add .worktrees/ui-<slug> -b ui-redesign/<slug> [起點]`。
4. 依賴（**例外：此步的 `npm ci` 以該 worktree 絕對路徑為 `workdir`**，timeout 600000；
   若原來已 junction node_modules，**必先拆除連結** `cmd /c rmdir .worktrees\ui-<slug>\node_modules`
   再執行 `npm ci`，否則會覆寫到主工作區 node_modules）。
   - 任務會改動 `package.json`／lockfile → 在 worktree 內以**專案環境**執行 `npm ci`。
   - 否則 junction 主工作區 `node_modules`（`-Target` 必須是**絕對路徑**）。
5. kit junction（指令同情境一第 2 條，目錄為 `.worktrees/ui-<slug>`），建立後 `Test-Path` 確認為 `True`。
6. 複製 `.env`（`Copy-Item .env .worktrees/ui-<slug>/.env`）。
7. 記下 worktree **絕對路徑**與比較基準；**之後工作期間的 bash**（test/lint/build、dev server、產物與
   測試檔讀寫、developer 編輯、QA 瀏覽器工作、git add/commit、交付與清除前的 git status）
   **一律以該 worktree 絕對路徑為工作目錄（bash 的 `workdir` 參數）**；
   worktree 的建立、**清除全程**、commit 後的 merge 依 §7.3 例外清單在主工作區執行。

**清除**（在主工作區根目錄執行；順序固定，**不可跳過拆連結**）：

1. **產物未 commit 時先經使用者明確同意丟棄**；在 worktree 內執行 `git status --short` 確認未追蹤產物並回報。
2. `cmd /c rmdir .worktrees\ui-<slug>\node_modules`（只拆 node_modules 連結；實體目錄或不存在的路徑會失敗，失敗可忽略）。
3. `cmd /c rmdir .worktrees\ui-<slug>\.opencode\ui-redesign-kit`（拆 kit junction；
   **失敗即中止清除並回報**——連結未拆則下一步可能跟隨刪除主工作區 kit。
   判準：若路徑本來不存在 → 視為已拆除；若存在但 rmdir 失敗 → 中止）。
4. `git worktree remove --force .worktrees/ui-<slug>`（--force 會刪除未追蹤檔）。
5. `git worktree list` 確認；分支 `ui-redesign/<slug>` 依使用者決定保留或刪除（刪除需確認）。

> 警告：若 node_modules 是 junction，直接 `git worktree remove --force` 在 Windows 上可能跟隨連結，
> 把主工作區的 node_modules 內容一併刪除——**絕不可跳過第 2 步**；kit junction 同理（見情境一警告）。

## 9. 產物與目錄規範

**產物根目錄由 ui-profile 指定**（欄位「產物」，預設 `docs/ui-redesign/`；安裝時同步 §11 樣式）。以下以預設值示範：

```
<產物根目錄>/<頁面slug>/
├── functional-baseline.md     功能基準（進版控）
├── design-spec.md             設計規格；每項標註來源等級：可確認／量測推估／需要設計決策（進版控）
├── design-tokens.json         具名 token：顏色、字級、字重、行高、間距、圓角、陰影、邊框（進版控）
├── component-mapping.md       新舊元件對照與復用方案（進版控）
├── pending-questions.md       待確認清單＋使用者決策紀錄（進版控）
├── visual-report.md           最終視覺報告（進版控）
├── functional-report.md       功能回歸報告（進版控）
├── code-review.md             程式審核報告（進版控）
├── scripts/                   客製回歸腳本（進版控，可累積成回歸資產）
└── .artifacts/                截圖、overlay、diff PNG（gitignore，不進版控）
    ├── r1/                    每輪一個專用子資料夾
    │   ├── 1440x900-actual.png、1440x900-overlay.png、1440x900-diff.png
    │   └── …
    └── r2/ …
```

- 文字產物進版控（是改版的正式文件）；截圖 PNG 每輪數 MB，**不進 git**，放 `.artifacts/`。
- **決策 D1（產物版控 vs 本專案 .gitignore）**：本專案 `.gitignore` 目前以 `/docs/` 忽略整個 docs
  （註記為「專案規劃文件不納入版控」），且 git 無法在被忽略目錄下重新包含子路徑。兩個方案：
  - **方案 A（預設，需使用者同意）**：把 `/docs/` 改為精確規則，讓產物進版控、其餘 docs 維持忽略：
    ```
    /docs/*
    !/docs/ui-redesign/
    /docs/ui-redesign/*/.artifacts/
    ```
    （註解同步更新說明產物文件納入版控的原因。）
  - **方案 B**：不動 `.gitignore`，ui-profile 的「產物」欄位改指到 repo 內已追蹤位置的新資料夾
    （例如 `ui-redesign-docs/`），代價是與「文件放 docs」的直覺不一致。
- 階段 5 的 commit 內容**包含產物文件**（orchestrator 用 `git add` 指定具體檔案，在 worktree 內執行）；
  **清除 worktree 前必須確認產物已 commit 或經同意丟棄**（§8.4、§8.5）。
- design-tokens.json 為框架無關 JSON；實作時由 developer 映射到專案樣式機制。
- 「先定標準再套用」：design-analyzer 量測值先彙成 tokens 供使用者確認（§7.1 階段 1.5），避免同名間距各頁數值不一。

### 10.1 ui-redesign/orchestrator（primary）

- 開場鐵律：讀 ui-profile；無則走範本蒐集程序並經使用者確認。
- 七階段流程、派工規則、並行與序列化規則（§6.3、§7）。
- 輪數控制、邊界行為、異常處理（§8）；worktree 程序（§8.5 情境一／二）。
- **有 worktree 時的工作目錄**：工作期間的 bash（test/lint/build、dev server、產物與測試檔讀寫、

  `workdir`；worktree 建立、**清除全程**、commit 後的 merge 依 §7.3 例外清單在主工作區執行。

- 產出（僅限自己頁面資料夾的四個檔名）：design-spec.md（區域→區塊→元件，每項含數值＋來源等級）、

- **決策回寫職責**（§7.1 階段 1.5）：使用者裁決後由它（重派）把決策寫回 pending-questions.md 並修訂

### 10.3 ui-redesign/developer

- 輸入：**五份產物文件必讀**——design-spec.md、design-tokens.json、component-mapping.md、
  **functional-baseline.md**、pending-questions.md——＋本次批次範圍＋（第 N 輪）ISSUES。
  **缺 functional-baseline.md 不得進入實作**。
- 實作原則：先 component-mapping 決定復用 → 引用 design-tokens → 分批小步修改 → 禁改區確有必要時
  **停手回報原因與影響範圍，由使用者決定**。
- 回歸防護（通用化既有 developer.md 精神）：全部測試基準線不低於、影響範圍分析（grep 所有使用處）、
  不削弱既有測試、保留既有檔案換行字元。
- **shell 鐵則**：不得以任何 shell 方式（重新導向、`Set-Content`、腳本等）寫入 `.env*` 與 `.opencode/**`
  ——edit 權限已 deny（含 worktree 前綴），shell 繞道一律視為違規（此為多層防護之一，非唯一防線，見 §15.7）。
- **edit 一律使用相對路徑**（相對 session 工作根；session 工作根預期在 worktree 內，見 §7.3 A1 決策），不使用絕對路徑（若 §17 實測發現 session 根無法進 worktree，則回退為絕對 worktree 前綴，見 §7.3 fallback）。
- 固定回覆格式：變更摘要／異動檔案清單／已執行驗證與結果／影響範圍分析／回歸檢驗／建議手動回歸檢查。
- 禁止（shell deny 落實，見 §11）：git commit/push/merge/rebase/reset/checkout/switch/worktree/clean/stash、

  `.opencode/**`、`.env*`、`.worktrees/**/.opencode/**`、`.worktrees/**/.env*`。

### 10.4 ui-redesign/visual-qa

- 方法論：shot（每頁 × 每 Viewport，等待條件固定、依 ui-profile「頁面進入前置」帶入 storageState 後再截）→
  diff（`--align width` 內建對齊＋差異百分比）→ **看圖判讀**差異 → 分類嚴重度與位置 → visual-report.md。
- 報告固定格式：`VERDICT: PASS | FAIL`、ISSUES（`- [嚴重度] 位置 - 說明、證據圖路徑、建議修正範圍`）、剩餘限制。

  修正建議限定視覺範圍（不動 API 與業務邏輯）；不得以範例數值冒充實測。
- **edit 一律使用相對路徑**（相對 session 工作根；session 工作根預期在 worktree 內，見 §7.3 A1 決策）。
- 權限：程式碼唯讀；edit 僅允許 visual-report.md 與 `.artifacts/**`（雙前綴）；shell 僅允許 shot/diff

### 10.5 ui-redesign/functional-qa

- 雙模式：`baseline`（階段 1）與 `regression`（階段 4），見 §7.2。

  補特徵測試（舊版先通過，寫入專案測試目錄——worktree 情境寫入該 worktree 內的測試目錄）→
  寫回歸腳本（放 `scripts/`）→ 跑全部測試記基準線 → functional-baseline.md。
- regression：重跑回歸腳本（經 `run.cmd`）＋全部測試＋build → 對照基準 → functional-report.md

- **客製腳本契約**：首次執行任一腳本前，於回覆中列出路徑與用途（§6.2 已知邊界的把關之一）。

### 10.6 ui-redesign/reviewer

- 審核清單：lint（基準線讀 ui-profile；**僅對異動檔案，不可 `--fix`**）→ 全部測試 → build →
  需求符合度（五步驟，見下）→ XSS/安全通用清單（對照 ui-profile「安全不變量」）→ 樣式污染
  （全域選擇器/CSS 變數影響面）→ 非預期改動（`git diff --stat` 對照、換行字元轉換偵測）。
- **需求符合度驗證**（每步引用文件位置＋程式碼位置為證據）：
  1. 逐項對照 design-spec.md：每個區塊/元件規格是否落實（如 token 引用而非寫死數值）。
  2. 對照 component-mapping.md：宣稱復用的元件是否真的復用、事件接線是否照 functional-baseline.md 保持。
  3. 禁改區檢查：diff 範圍內是否碰 API 契約/store/socket/路由資料流（未經核准即問題）。
  4. 需求外改動偵測：spec 與 mapping 都沒提到的修改 →「非預期改動」（一般級）。
  5. 重審時逐項確認上輪 ISSUES 真的修好（查證修正方式，不採信口頭）。
- spec 模糊導致無法判斷時列「疑問」，不直接判錯。
- `git fetch` 僅用於更新遠端參照，**不得帶 refspec 更新本機分支**。
- **shell 指令逐條執行**（不使用 `&&`／`;`／`|` 串接；§11 deny 串接，參數值不含字面 `;`、`|`），多次呼叫代替。
- **edit 一律使用相對路徑**（相對 session 工作根；session 工作根預期在 worktree 內，見 §7.3 A1 決策）。
- 輸出：`VERDICT: PASS | FAIL`＋嚴重度三級＋固定格式（骨架沿用既有 reviewer.md，通用化），
  **審核報告寫入自己頁面資料夾的 `code-review.md`（唯一寫入例外）**，程式碼一律唯讀。

## 11. 權限模型（V2 有序規則，可直接落地）

**語意要點（OpenCode V2）**：`permissions` 為有序規則列表，**最後匹配者生效**；內建基底是全部允許，
因此要收斂權限必須**先列寬 deny、再列例外 allow；寬 allow 必須排在它所涵蓋的破壞性窄規則之前**
（窄規則在後才會覆蓋寬規則，例如 `git branch*` allow 之後才接 `git branch -d*`／`-D*` ask）。
shell 資源是原始指令字串比對，例外規則必須**自帶 `*` 萬用字元**；`subagent` 的 resource 必須是**完整 agent ID**。
`**` 的跨層級匹配行為、`*` 前空格語意、**絕對路徑在 edit 資源的匹配行為**（是否觸發 ask／allow）
**列入實作必測**（§17），依實測結果統一寫法。
`read`／`glob`／`grep` 為唯讀工具，維持預設開放，本表不收斂。

**雙前綴樣式（worktree 相容）**：OpenCode 的 edit 路徑比對相對 session 工作根目錄。worktree 情境下產物與
測試檔位於 `.worktrees/<名稱>/…`，因此**每條 edit 例外都成對提供**：
`<產物根目錄>/…`（主工作區／無 worktree 情境）＋ `.worktrees/**/<產物根目錄>/…`（worktree 情境）；
functional-qa 的測試檔 ask 同樣成對（`test/**` ＋ `.worktrees/**/test/**`）。
下方以「×2 前綴」標示，**實作時逐條展開成兩條規則**。展開範例（design-analyzer 的 design-spec.md 一條）：

```yaml
- { action: edit, resource: "docs/ui-redesign/*/design-spec.md", effect: allow }
- { action: edit, resource: ".worktrees/**/docs/ui-redesign/*/design-spec.md", effect: allow }
```

**工具呼叫白名單**：每個工具同時提供反斜線與正斜線兩條（模型可能自動改寫格式）：
`cmd /c .opencode\ui-redesign-kit\tools\<工具>.cmd *` 與 `cmd /c .opencode/ui-redesign-kit/tools/<工具>.cmd *`。
防串接：唯讀 agent 在工具 allow **之後**加 `{ action: shell, resource: "*&&*", effect: deny }`、
`{ action: shell, resource: "*;*", effect: deny }`、`{ action: shell, resource: "*|*", effect: deny }`、
`{ action: shell, resource: "*&*", effect: deny }`。

## 12. 指令介面

`/ui-redesign` 命令（`ui-redesign-kit/commands/ui-redesign.md`，安裝時複製到 `.opencode/commands/`）。

## 13. 模型配置建議（github-copilot provider，可調；完整格式 `provider/model#variant`）

| Agent | 建議 model | 理由 |
|---|---|---|
| ui-redesign/orchestrator | `github-copilot/claude-sonnet-5.5#xhigh` | 同既有 orchestrator，流程決策複雜 |
| ui-redesign/design-analyzer | `github-copilot/claude-sonnet-5.5#high` | 多模態＋量測細度要求高 |

## 14. 與既有 3-Agent 團隊的關係

- 兩套團隊**完全獨立**：各自 primary agent、各自 subagent 白名單、互不修改對方檔案。
  既有 orchestrator 的 subagent 白名單僅有 `developer`／`reviewer`（無法呼叫 ui-redesign/*）；
  **新團隊所有 agent 的 `subagent` 權限一律先 `deny *`；唯一能派工的是 orchestrator，且僅限
  5 個完整 ID 例外**（§11）——任何 agent 無法再派工，分工由權限層強制，不依賴指令自覺。
- 既有團隊已驗證的機制以「通用形式」融入新團隊：VERDICT PASS/FAIL、嚴重度三級、3 輪上限、
  commit 訊息先審核、worktree 詢問與清除程序（含 junction 警告）、回歸防護精神
  （基準線／影響範圍／特徵測試／不削弱測試／換行字元保留）。
- **instructions 注入的相容**：專案 instructions 會進入所有 agent 上下文。新 subagent 正文以 §5.1 的
  職責聲明處理潛在衝突（worktree／commit 事項只歸 orchestrator）。
  （可選強化：經使用者同意後，在 workflow-rules 的例外名單明確加入 ui-redesign/ 團隊——本期不做，見 §16。）
- 職責重疊的劃分：既有 `reviewer`（功能開發審核）與 `ui-redesign/reviewer`（UI 重構審核）格式同源但檔案獨立；
  一般功能開發不會用到 ui-redesign/ 團隊，UI 重構不會用到既有團隊。

## 15. 風險與已知限制

1. **像素比對的極限**：字體渲染、反鋸齒、螢幕縮放會造成偽差異；差異百分比是參考值不是品質保證，判讀以疊圖為準。
2. **靜態素材的天然限制**：單張圖片無法涵蓋 hover／focus／載入中／RWD／捲動等狀態——靠 pending-questions 決策點補齊，HTML 原型能縮小但無法消除此限制。
3. **Node 版本並存**：工具鏈依賴 `.tool-node.cmd`（由安裝程序依 ui-profile 產生）；路徑失效時依安裝指南重新產生，不自行改用其他 Node。
4. **瀏覽器單一資源**：三個角色的瀏覽器工作必須序列化，是流程中的等待點。
5. **登入態隔離的代價**：Playwright Chromium 與使用者日常環境完全隔離，需認證頁面靠使用者提供的
   storageState 檔（§5.2、§6.2）；無法取得時該頁驗證受限，如實標註並列入手動回歸清單。
6. **客製腳本的執行邊界**：`run.cmd` 執行的腳本以工具用 Node 執行＝具備完整 Node 能力（可寫檔）。
   防護：工具端路徑驗證（§6.2 輸出契約：realpath、拒 `..`／符號連結脫離、僅 `<產物根目錄>/<slug>/scripts/`
   子樹，接受 worktree 內對應路徑）＋functional-qa 首次執行前回報契約＋安裝指南告知。此為已知且接受的邊界。
7. **shell 串接的防護層級**：唯讀 agent 以權限層 deny（`&&`、`;`、`|`、`&`）＋正文禁令＋工具 CLI
   只接收檔案路徑（URL 經 `--url-file` 參數檔傳入，見 A2 決策 §6.1）＋工具端輸出路徑驗證四層防護；
   developer／orchestrator 的 shell 較寬（設計取捨），`.env`／`.opencode`（含 worktree 前綴）保護以
   edit deny＋正文鐵則＋reviewer 偵測構成，非完全強制。
8. **多頁大批次**：一次任務目標頁過多會拉長輪次；建議以頁面為單位分批執行（每批一份產物資料夾）。
9. **ask 授權的取捨**：functional-qa 寫專案測試檔、orchestrator 的動態 shell 指令都會跳 ask——通用性與
   安全的取捨，代價是多幾次確認。**child session 中 ask 是否會回到主 TUI 供使用者點選，需實作時驗證**（§17）。
10. **本專案 kit 不進版控**：`.opencode/` 被既有 .gitignore 忽略（使用者既有規則），kit 檔案僅存本機；
    搬家從本機複製。產物版控見決策 D1。
11. **kit junction 的資料安全**：worktree 清除時 kit junction 必須在 `git worktree remove` 之前拆除
    （§8.5），且 **rmdir 失敗即中止、不可繼續**——被跟隨刪除會連主工作區的 `.opencode/ui-redesign-kit`
    （gitignore，無版控可還原）一併刪除。
12. **workdir 白名單**：worktree 的建立、清除全程、commit 後的 merge 必須在主工作區執行；
    其餘工作期間操作在 worktree 內執行（§7.3）。特別是 `git add`/`git commit` 必須在 worktree 內，
    因為分支只 checkout 在 worktree。

## 17. 實作範圍與必測項（下一步）

依本設計書產出實作計畫，預計交付：

1. 6 個 agent 檔案（`.opencode/agents/ui-redesign/`，§10 綱要＋§11 權限，雙前綴樣式逐條展開）
2. kit 資料夾（`ui-profile-範本.md`、`安裝指南.md`（含 §5.3 安裝必改清單）、`commands/ui-redesign.md`）
3. tools 工具包（`shot`／`diff`／`run`／`codegen`／`setup`，package.json，`.tool-node.cmd` 產生機制，
   Playwright Chromium 初始化，§6.2 CLI 契約與路徑驗證）
4. 本專案的 `.opencode/ui-redesign-kit/ui-profile.md`（依本專案實況填寫）
5. **決策 D1 落地**：.gitignore 調整（方案 A，需使用者同意）或 ui-profile 改產物根目錄（方案 B）

### 17.1 使用者裁決事項（A 級）

| 決策 | 選項 | 落地位置 |
|---|---|---|
| A1：worktree 情境的 edit 路徑策略 | **方案①**：subagent 的 session 工作根進 worktree，edit 使用相對路徑（如 `src/...`、`docs/ui-redesign/...`）；若 §17 實測發現 OpenCode 不支援，則回退方案② | §7.3 session 工作根原則、§10 各 agent、§11 權限樣式保留雙前綴作 fallback |
| A2：URL 參數傳遞 | **方案①**：URL 先寫入 gitignored 參數檔（`<slug>/.artifacts/url-args.json`），工具以 `--url-file` 接收檔案路徑 | §6.1 URL 傳遞契約、§6.2 shot/codegen 參數表 |

### 17.2 實作階段待處理問題（B 級，納入實作清單）

- **情境一 npm ci 閘門**：把情境二「拆 node_modules junction 再 `npm ci`」的規則複製到 §8.5 情境一的依賴處理步驟。
- **D1 與 `git status --short` 的互動**：`.gitignore` 若仍忽略 `/docs/`，空輸出會掩蓋未 commit 產物。落地 D1 後，清除閘門改用 `git status --short --ignored` 或 `git check-ignore*`；若用後者，需在 orchestrator 權限加 `git check-ignore*` allow。
- **主工作區根推導**：範例程式碼要先 `fs.realpathSync` 再向上三層，特別是 kit 為 junction 時。
- **§8.5 情境二清除標題**：小標「皆在主工作區根目錄執行」與步驟 1「在 worktree 內 `git status --short`」不一致，實作時以步驟內文為準。

### 17.3 必測項（實作驗證清單）

- **session 工作根實測**：OpenCode subagent 傳入 `workdir` 後，`edit`/`read`/`glob`/`grep` 的 session 工作根是否真的移到該目錄；若否，啟動 §7.3 fallback（絕對 worktree 前綴）。
- shell 樣式空格語意實測（`git status *` 與 `git status*` 的差異）、`**` 跨層級匹配行為、
  「最後匹配生效」語意、**絕對路徑在 edit 資源的匹配行為**——依實測結果統一白名單寫法。
- child session 的 `ask` 是否回到主 TUI（§15.9）。
- 串接 deny 實測：`&&`、`;`、`|`、`&` 四種（含含空格與不含空格形式、換行續行是否被視為同一指令）。
- URL 參數檔實測：`.cmd` 接收 `--url-file` 路徑、Node 讀取 JSON、工具正確開啟 URL；確認 shell 字串不含 `&;/|`；
  **agent 端以 edit 寫入 `<slug>/.artifacts/url-args.json` 可被 edit allow 命中**（design-analyzer／visual-qa／functional-qa 三者）。
- worktree 情境：kit junction 後 tools 可執行；`.worktrees/**/<產物根目錄>` 的 edit 樣式可匹配；
  `.worktrees/**/test/**` 的 ask 可觸發（特徵測試寫入隔離區；此項在方案① fallback 時驗證）。
- `run.cmd`／shot／diff 的路徑驗證（輸出契約：`..`、符號連結、範圍外路徑一律拒絕；worktree 內路徑接受；
  輸入路徑唯讀不寫入；區段邊界前綴比對）。
- 主工作區根推導演算法（§6.2）與 junction 情境實測（先 realpath 再向上三層）。
- `commands/ui-redesign.md` 的 frontmatter 欄位（`agent`、`subagent`）依官方 commands 文件核對。
- developer 延續用的 sessionID 欄位名依官方文件核對。
- agent 可見性確認（6 個 ID 正確顯示）。
- （可選）單頁試跑。
