# 使用手冊（安裝完成後的日常操作）

> **定位**：本檔是安裝完成後的**日常操作說明**（使用者視角）。安裝與設定問題見 `安裝指南.md`；完整設計規格見 repo 的 `docs/2026-11-11-UI重構Agent團隊-設計書.md`。
> 對象：在已安裝本套件的前端專案中，使用 `/ui-redesign` 執行 UI 重構任務的人。

---

## 1. 開始前的確認清單

| 確認項 | 檢核方式 |
|---|---|
| `ui-profile.md` 已填寫 | `Test-Path .opencode/ui-redesign-kit/ui-profile.md` 為 True |
| 工具鏈已初始化 | `tools/.tool-node.cmd` 存在；shot／diff `--help` 可執行 |
| 6 個 agent 可見 | OpenCode 輸入 `@` 或 agent 清單看到 `ui-redesign/orchestrator` 等 6 個 ID |
| 目標頁可進入 | dev server 指令可用；需登入的頁面備妥 storageState 檔（gitignored 路徑） |
| （可選）命令檔已裝 | `Test-Path .opencode/commands/ui-redesign.md` 為 True |

## 2. 發起任務

**方式一（已裝命令檔）**：直接輸入 `/ui-redesign`：

```
素材：<PNG/JPEG 設計圖／HTML 原型路徑或網址／規格文件位置，可多行>
目標頁面：<頁面清單，如：登入頁（/login）>
特別要求：（可省略，如：保留既有表單驗證邏輯）
```

**方式二（未裝命令檔）**：把 primary agent 切換為 `ui-redesign/orchestrator` 後，下達同樣內容。

素材與目標頁面**缺一時 orchestrator 會反問你**，不會自行推測。

> **多頁批次**：建議一次任務只做一頁（每頁一份產物資料夾），完成後再開下一頁——批次過大會拉長視覺迴圈輪次。

## 3. 流程中會發生什麼（七階段 × 你的參與點）

```
階段 0 準備 → 1 基準建立（含功能對照閘門）→ 1.5 設計與功能取捨決策點 → 2 實作 → 3 視覺迴圈 → 4 驗收 → 5 交付
```

### 階段 0：準備

- orchestrator 讀 ui-profile（不存在會用範本問你逐欄補齊，**經你確認後才開工**）。
- **會問你**：是否使用 git worktree 隔離區（要／不要）。
  - 「要」：確認目的分支及其實際工作目錄，在 worktree 外的 ignored 本機位置保存來源／目的 docs 的完整路徑、存在狀態、SHA-256 與內容快照，再建立 `.worktrees/ui-<slug>`，將原 docs 複製為起點。
  - 「不要」：直接在主工作區進行，仍保存本機 docs 快照供審核，產物原地保留、不需跨目錄同步。
- **會問你**（若 port 已占用）：沿用你手動開的 dev server，或由 orchestrator 另開 port。沿用時收尾不會動它。

### 階段 1：基準建立（兩個 agent 並行，你等待）

- `functional-qa` 盤點既有功能（每個功能建立 `F-xx` 固定 ID）、補特徵測試、寫回歸腳本、記錄測試基準線。
- `design-analyzer` 解析素材產出設計規格、tokens、元件對照（含功能涵蓋對照、新增功能對照）、待確認清單（PQ／FQ／NF）。
- **功能對照閘門（雙向）**：兩者回報後，orchestrator 逐項核對——正向看 baseline 的每個 `F-xx` 是否都有 component-mapping 對照、設計未涵蓋或只涵蓋部分者是否都有 FQ；反向看設計稿新增的互動功能是否都有 `NF-xx` 與待裁決項，並把每個 NF 與 `F-xx` 交叉比對（其實是既有功能者撤銷 NF、改開 FQ）。缺漏會重派 design-analyzer 補齊（新 session、不計輪），**閘門未過不會進階段 1.5**。
- **互動點**：`functional-qa` 完成後，orchestrator 會把**測試檔清單（檔案＋用途）**與 **`F-xx` 功能清單（ID＋名稱）**用 question 給你確認（ask 在子 session 實測不生效，改由流程把關），並問「是否有漏列的既有功能？」。拒絕的測試檔項目會撤回、該功能改列「建議手動回歸」；若有漏列功能，`functional-qa` 會以附錄補 `F-xx`（不重編）後重跑功能對照閘門。若閘門缺口無法補齊，也會問你補件或裁決。

### 階段 1.5：設計與功能取捨決策點（**你需要裁決**）

- orchestrator **先問 FQ（功能取捨），再問 NF（新增功能），最後問 PQ（設計決策）**。
- 每個 FQ 會說明：功能 ID、舊行為、設計缺口、移除影響、選項（保留／移除／調整／另案）。四種裁決的後果：
  - **保留**：既有功能繼續存在；若設計稿沒有視覺規格，design-spec 會新增「設計外保留（依使用者裁決）」，寫明位置、視覺處理與來源等級。
  - **移除**：功能與相關入口／行為移除；相關測試調整仍需你同意，報告會註明「因需求而改」。
  - **調整**：保留功能但依裁決改變呈現／行為，需有明確視覺規格。
  - **另案**：本次不變更該功能（維持現狀）並另立任務追蹤；若連維持現狀都不可行，會回到 FQ 重新裁決。若專案沒有 issue tracker，則以交付的「功能取捨清單」作為後續追蹤依據，由你建立後續任務。
- 每個 NF（新增功能）會說明：設計所見、舊版現況、需要哪些新 API／事件／資料流、選項（納入／不納入／另案）。三種裁決的後果：
  - **納入**：本次要做；design-spec 會寫實作規格。標註「超出 UI 還原範圍」者，規格只會寫「待你提供／另立任務」，不會偷做半套。
  - **不納入**：本次不做；設計稿多畫的部分由 design-spec 註明「依 NF 裁決不納入」，程式與畫面都不會出現該互動。
  - **另案**：本次不實作，另立任務追蹤。
- 你逐項裁決後，由 design-analyzer 把決策**寫回** pending-questions.md、同步 component-mapping.md 的處理狀態，並修訂規格。
- **會問你**：確認 `design-spec.md` 與 `design-tokens.json` 兩者。**凍結條件：所有 FQ／NF 已裁決＋baseline 功能全部有對照＋FQ 移除項已清除或標註「依 FQ 移除」＋另案維持現狀且仍可見者已列設計外保留＋NF 納入項已寫實作規格（或已標註「待你提供／另立任務」）、不納入／另案項未留規格**；保留／調整／納入項若缺規格會退回補齊或拆新 PQ 再問，不得直接凍結。確認後進入實作，之後要改規格需再走一次確認。

### 階段 2：實作（你等待）

- `developer` 分批修改（先 tokens／共用元件 → 頁面分區），優先重用既有元件與邏輯。
- 實作前會先做**功能取捨預檢**：baseline 每個 `F-xx` 都要有 mapping 對照，設計未涵蓋者要有已裁決的 FQ；每個 `NF-xx` 也都要已裁決（納入者要有 design-spec 規格，或標註「待你提供／另立任務」）；缺漏就停手回報。
- **不得以「設計稿沒畫」為由移除、隱藏或停用既有功能**；只能依 FQ 裁決處理。保留但規格沒有視覺處理時會停手回報。
- **也不得以「設計稿有畫」為由自行新增功能**；只能依 NF 裁決處理。不納入／另案者一律不做，標註「超出 UI 還原範圍」者不得實作（會記為「納入待後端」，交付時列後續任務，不會讓整批停擺）。
- 若 FQ 裁決會導致測試／回歸腳本刪除或改寫，developer 會先提出「FQ 測試調整清單」（類別、檔案、FQ、原因、扣除數、替代測試）；orchestrator 會逐項問你同意，**優先改寫維持項數**，你同意後才可刪改。
- 碰到禁改區（API 契約／store／socket／路由資料流）時會**停手回報**，由你決定放行與否。

### 階段 3：視覺迴圈（每輪看圖判讀，最多 3 輪）

- `visual-qa` 每輪產出：`visual-report.md`＋該輪 `.artifacts/r<N>/` 的截圖／overlay／diff 圖。
- `visual-qa` 會收到**設計外保留清單**（design-spec「設計外保留（依使用者裁決）」＋FQ 保留／調整／另案（維持現狀）項）與 **NF 裁決清單（含 `x2` 標記）**：實際畫面有設計稿未涵蓋但已裁決保留／調整／另案維持現狀的區塊，不會被判為視覺缺陷，而是記入「設計外保留項」；NF 裁決納入且後端到位者照 design-spec 判讀，不納入／另案卻仍出現會列 ISSUES，而裁決不納入／另案或「納入待後端（`x2`）」、設計稿有畫但畫面正確地沒有的，會記入「NF 已裁決未出現項」且不列為缺漏；若多出未記載的區塊（或 NF 尚未裁決但設計稿有畫），會列「需要確認」，不會直接建議刪除。
- **「需要確認」非空時，orchestrator 必須先問你**那是什麼、是否為既有功能漏列或設計外新元素；前者會補 `F-xx`／FQ 並重跑閘門（若新增 FQ 會先問你裁決），後者會依性質補 **NF**（新增互動功能）或 PQ／design-spec（純視覺），或請 developer 修正。
  - **裁決保留／另案維持現狀**：design-analyzer 更新 design-spec「設計外保留」與 component-mapping → 若 design-spec／tokens 有變更，會請你重新確認 → 重跑功能對照閘門（確認 mapping／FQ／NF 一致）→ 再重跑視覺（該區塊應改列設計外保留項）。不需 developer 改畫面。
  - **裁決移除／調整**：design-analyzer 更新規格與 mapping → 若 design-spec／tokens 有變更，會請你重新確認 → orchestrator 派同一個 developer session 修正實際畫面；若涉及測試／腳本，走「FQ 測試調整清單」與你的同意流程 → 重跑功能對照閘門 → 再重跑視覺比對。
  - **設計外新元素且需要新 API／事件／資料流**：建 `NF-xx` 並標註「超出 UI 還原範圍」，由你決定納入（後端能力要到位）、不納入或另案，不會自行實作。
- **若新增 FQ／NF 或 design-spec 有變更，完成裁決回寫後會請你重新確認 `design-spec.md` 與 `design-tokens.json`，才續跑後續的功能對照閘門／視覺比對；此為決策點處理，不計視覺輪數。** **「需要確認」未清空前不會進階段 4。**
- 你可隨時打開 overlay／diff 圖核對；**差異百分比是參考值（預設門檻 <2%），判讀以疊圖為準**。
- **第 3 輪仍未過時，會問你四選項**：
  1. 再修一輪（每次 +1 輪，不自動續跑）
  2. 裁決差異可接受（帶未解項進驗收，記入「剩餘限制」）
  3. 你自己手動調整（保留現狀，之後重跑比對）
  4. 暫停任務（worktree 位置與分支會保留）

  > 「需要確認」未清空前，即使選「裁決差異可接受」，也不會進階段 4。

### 階段 4：驗收（兩條線序列化，你等待＋看結果）

- 先 `functional-qa`：orchestrator 會帶**已同意測試調整清單**；functional-qa 建立並使用**調整後基準**（原始基準 − 經你核准扣除的測試／腳本；無扣除時即原始基準），重跑回歸腳本＋全部測試＋build＋**功能取捨對照＋新增功能對照** → `functional-report.md`。不得少於調整後基準、不得有失敗。未經裁決的功能缺失列 FAIL（嚴重）；依裁決移除／改行為註記「因需求而改」；裁決保留／調整／另案維持現狀但功能缺失、隱藏或停用列 FAIL（嚴重）；功能仍在但行為偏移或裁決未落實列 FAIL（一般），若影響主要操作流程、資料正確性、API 契約或安全則升級為嚴重。新增功能方面：未經 NF 裁決就出現列 FAIL（嚴重）；裁決納入但缺失／不可用列 FAIL（嚴重）；裁決不納入／另案卻仍存在列 FAIL（一般）。**例外：裁決納入、標註「超出 UI 還原範圍」、後端能力未到位、程式沒有入口也沒有假資料（交付時列為後續任務）→ 記為「納入待後端（`x2`）」，不算 FAIL。**
- functional-qa 判定：任一 FAIL 條件（測試／腳本低於調整後基準、build 失敗、`e > 0`、`w > 0`、未經核准刪改測試／腳本、裁決未落實）即 FAIL；全部通過且 `e = 0`、`w = 0` 才 PASS。`x2`（納入待後端）不計入 FAIL，但必須註明後續任務。
- 後 `reviewer`：lint／測試／build＋需求符合度六步驟（含**功能取捨與新增功能查核**、調整後基準、測試與 `scripts/` diff）＋XSS/安全＋樣式污染＋非預期改動 → `code-review.md`。裁決保留／調整／另案維持現狀但功能缺失、隱藏或停用列「嚴重」，未經裁決就新增的功能列「嚴重」；**「納入待後端（`x2`）」同樣不算 FAIL（與 functional-qa 同一判定）**；功能仍在但行為偏移、裁決未落實或僅文件／測試標註不一致列「一般」，影響主要操作流程、資料正確性、API 契約或安全時列「嚴重」。
- 任一 FAIL → 指定範圍退回 developer → 重跑對應驗收（驗收另有獨立的 3 輪預算）。
- 視覺退回後若動了樣式／template，orchestrator 會加跑一次快速視覺比對（不計輪）。

### 階段 5：交付（**你需要審核**）

- 彙整固定五項：三份報告結論、**功能取捨清單**（FQ：裁決、測試／腳本調整、扣除數、同意依據與調整後基準；NF：裁決、實作結果、「超出 UI 還原範圍」後續任務）、剩餘限制與待確認事項、修改檔案清單、建議手動回歸清單。
- 功能取捨統計公式：`T = f + a + b + c + d + e`（f＝已涵蓋、a＝保留、b＝調整、c＝移除、d＝另案、e＝未裁決缺失，PASS 時 e 必須為 0）；表格每列對應一類，`未裁決缺失（FAIL）` 對應 e。新增功能統計：`TN = x + x2 + y + z + w`（x＝納入已落實、x2＝納入待後端、y＝不納入、z＝另案、w＝未裁決卻出現，PASS 時 w 必須為 0）。
- **「需要確認」正常應為 0；未清空前不會進階段 4，因此不會進交付。**若你明確裁決接受某項，該項會由 design-analyzer 收進 design-spec「設計外保留」或 PQ 紀錄，重跑視覺後就不再是「需要確認」。交付的「剩餘限制」只列其他未解項（視覺未解、登入態未驗證等）。
- **最終驗收由你裁決**：看完最終輪 overlay／diff 圖與 visual-report 後決定。
- **會問你**：繁體中文 commit 訊息審核——同意才在工作目錄提交**非忽略的程式碼與正式測試**；docs／`.opencode/` 全部不提交。
- **會問你**：worktree 處理（合併並清除／保留／直接丟棄）。選保留不強迫合併、同步或清除。
- **合併並清除**：先看 docs 同步計畫；用 `git worktree list --porcelain` 找目的分支實際工作目錄（主工作區不一定是 main），經你同意合併程式碼。Git 成功後另做**本機檔案同步**，來源未改保留目的，雙方同改但內容不同交你裁決，來源刪除逐檔確認；不鏡像、不跟隨連結。同步逐檔驗證成功、回報目的 docs 絕對路徑／清單／未解項後，才可拆 junction／remove。
- 無基準／基準損壞、目的不存在／未 checkout／不明、路徑不安全、Git 合併衝突或同步失敗時停止並保留 worktree 與產物。直接丟棄須你明確同意**具體未保留資料清單**；一般 remove 同意不等於資料丟棄同意。
- **絕不 push**——需要時你自行 `git push`。

## 4. 互動點總表（什麼時候會找你）

| 時機 | 形式 | 內容 |
|---|---|---|
| 開工前 | question | worktree 要不要；ui-profile 缺失時逐欄補齊 |
| 階段 0 | question | port 占用時：沿用或另開 |
| 階段 1 | question | 測試檔清單＋`F-xx` 功能清單確認（含「是否有漏列既有功能？」）；功能對照閘門缺口無法補齊時，問你補件或裁決 |
| 階段 1.5 | question | **FQ 功能取捨裁決（先問）**；**NF 新增功能裁決（次問）**；PQ 設計決策裁決；規格與 tokens 凍結確認（需所有 FQ／NF 已裁決） |
| 階段 2 | question | 功能取捨預檢缺漏、保留／納入項缺規格、FQ 測試／腳本調整清單，或碰到禁改區時停手回報，由你裁決 |
| 階段 3 | question | 「需要確認」非空時問你區塊性質與處理方式（既有功能漏列／新增功能未建 NF／純視覺）；必要時 developer 修正畫面、FQ 測試／腳本調整經你同意；新增 FQ／NF／design-spec 變更時重新確認規格與 tokens；3 輪 FAIL 後的四選項 |
| 階段 4 | question（必要時） | 因 FQ 裁決需調整測試／腳本時，先問你同意；兩條線跑完你看報告（含調整後基準、功能取捨與新增功能對照） |
| 階段 5 | question | 非忽略程式碼／正式測試的 commit 訊息審核；worktree 處理、docs 同步計畫／衝突／刪除裁決（交付含 FQ＋NF、測試／腳本調整、剩餘限制） |
| 清除時 | ask | `worktree remove`、branch 刪除、merge、commit |

> orchestrator 在主 session 的動態 shell 指令（dev server、程序終止）與 commit／merge／worktree remove 仍會跳 ask，由你核准。

- **來源等級（原始三級＋使用者裁決）**：`可確認`（HTML 原型量測值）／`量測推估`（圖片目測，標信心度）／`需要設計決策`（決策點前）／`使用者裁決`（決策點後，token 為 `user-decision`）。**推估不等於確認**，驗收時可據此追問。

- ignored docs 沒有分支歷史，不會被 Git merge 帶回；保存根預設在主工作區 `.opencode/ui-redesign-local/<保存ID>/`，位於被清除的 worktree 外，包含來源／目的基準、審核快照、同步計畫、覆寫前備份與結果，不隨 worktree 刪除。`.opencode/` 不從 worktree 整層複製回去。完整安全步驟見 `worktree-procedures.md` §2。

## 6. 常用操作

- **暫停任務**：任何階段可要求暫停；worktree、dev server、產物全部保留，orchestrator 會回報暫停位置（分支與 worktree 路徑）。
- **續跑**：目前版本**沒有**續跑專用命令——切回 `ui-redesign/orchestrator` 後描述「接續上次的 UI 重構任務」＋提供暫停時的分支／slug 即可，orchestrator 會先盤點現況再續。
- **單頁重驗**：請 orchestrator「重跑 `<slug>` 的視覺比對」即可（快速比對不計輪數）。
- **修改後重驗**：你手動調整了樣式後，請 orchestrator 重跑一次視覺比對確認。
- **手動清理殘留 worktree**：**不要直接 `git worktree remove --force`**——先依 `worktree-procedures.md` 完成 docs 保存／同步驗證（或明確丟棄裁決），才依 node_modules → kit → remove 順序清除。kit 拆除失敗中止；node_modules 仍為 junction 或類型不明且拆除失敗也中止。保存根不清除。

## 7. 異常時怎麼辦

| 情況 | 處理 |
|---|---|
| dev server 啟動失敗 | orchestrator 停止並回報；你決定重試或中止（不會擅自跳過） |
| 沿用的 dev server | 收尾一律不終止，結束時會告知「沿用的 dev server 保留未動」 |
| 設計素材缺失／格式不符 | orchestrator 問你補件或裁決；agent 不推測、不虛構 |
| 你拒絕測試檔變更 | 該項停止並回報；功能改列「建議手動回歸」，之後可重跑或手動補 |

| 同一工具連續失敗 3 次 | 停止並回報你裁決 |
| 同一視覺問題連修 3 次無改善 | 提前停止，重新分析原因（可能要求重新量測），不盲目重試 |

## 9. 常見問題

**Q：為什麼階段 1 要花那麼久？** 防護網先織好（特徵測試＋回歸腳本）是套件的核心設計——改版後的功能保障靠這段建立，時間花在刀口上。

**Q：可以跳過決策點直接實作嗎？** 不建議。pending-questions 的決策（hover／RWD 等）沒有裁決，developer 只能推估，視覺迴圈會多打好幾輪；**FQ／NF 未裁決更不能跳過**，流程不會凍結規格。

**Q：新設計沒有舊功能 A 怎麼辦？** 不會自動消失。`functional-baseline.md` 會給 A 一個 `F-xx`，`component-mapping.md` 標「設計涵蓋：否」，並在 `pending-questions.md` 開 `FQ-xx`。階段 1.5 會先問你「保留／移除／調整／另案」並說明移除影響；未裁決不會凍結規格，developer 也不能自行刪掉 A。若你選保留但設計稿沒有視覺規格，`design-spec.md` 會補「設計外保留（依使用者裁決）」寫明位置與視覺處理。

**Q：新設計多了舊版沒有的功能 A 怎麼辦？** 不會被自動做進去。design-analyzer 會建 `NF-xx`（新增功能對照），`pending-questions.md` 開一筆 NF 問題；階段 1.5 會問你「納入／不納入／另案」，並說明需要哪些新 API／事件／資料流。未裁決不會凍結規格，developer 也不能自行「照設計稿做」。選納入但需要新 API／事件／資料流時會標註「超出 UI 還原範圍」，不會幫你偷做半套；選不納入／另案則程式與畫面都不會出現該互動。

**Q：怎麼分辨「新增功能」和「只是設計稿畫得比較好看」？** 判準是**有沒有新行為**：只有顏色、間距、圓角、陰影、字級等外觀差異 → 直接當規格實作，不建 NF；有新的互動、操作流程或資料呈現方式 → 一律建 NF。判斷不確定時一律列 NF，由你在決策點裁決（多問一次總比默默多做一個功能好）。

**Q：移除功能後測試變少，會不會被當成退化？** 不會，前提是有經你同意的「調整後基準」。FQ 裁決導致測試／腳本必須刪改時，developer 會先提清單、由 orchestrator 問你同意；`functional-baseline.md` 會記錄扣除項（FQ、原因、扣除數、替代測試、同意日期），functional-qa 與 reviewer 改用「原始基準 − 核准扣除」判定。未經核准的刪除或放寬仍會 FAIL／列問題。

**Q：為什麼測試檔不是每次跳核准，而是一次列清單給我確認？** 實測發現 ask 在子 session 會自動允許（沒有互動介面可詢問），所以套件改由 orchestrator 在階段 1 彙整「測試檔清單＋用途＋F-xx 功能清單」一次問你——保護仍在，只是形式從「逐檔核准」改為「清單確認」。階段 4 因 FQ 調整測試／腳本也走 question。

**Q：視覺達到門檻了，為什麼還問我驗收？** 差異百分比無法涵蓋「看起來對不對」（字體渲染、偽差異）；最終驗收永遠由人裁決，這是套件的鐵則。

**Q：push 是誰做？** 套件**絕不 push**，交付後由你自行 `git push`。

**Q：merge 成功就能清除 worktree 嗎？** 不行。ignored docs 沒有 Git 分支歷史，還要同步到目的分支實際工作目錄的 docs 並逐檔校驗。任何失敗或未解衝突保留 worktree；你可選保留，不必為了交付強迫合併／清除。

**Q：目的 docs 也改過或來源刪了檔案呢？** 來源未改時保留目的；雙方改成相同內容視為已同步，不同則停止由你裁決。來源刪除列清單請你逐項確認，不自動刪目的；目的獨有內容不鏡像移除，基準不明不靠時間戳猜測。
