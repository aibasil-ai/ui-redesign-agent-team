# 使用手冊（安裝完成後的日常操作）

> **定位**：本檔是安裝完成後的**日常操作說明**（使用者視角）。安裝與設定問題見 `安裝指南.md`；完整設計規格見 repo 的 `docs/2026-11-11-UI重構Agent團隊-設計書.md`。
> 對象：在已安裝本套件的前端專案中，使用 `/ui-redesign` 執行 UI 重構任務的人。

---

## 1. 開始前的確認清單

| 確認項 | 檢核方式 |
|---|---|
| `ui-profile.md` 已填寫 | `Test-Path .opencode/ui-redesign-kit/ui-profile.md` 為 True |
| 工具鏈已初始化 | `tools/.tool-node.cmd` 存在；shot／diff `--help` 可執行 |
| 6 個 agent 可見 | OpenCode 輸入 `@` 或 agent 清單看到 `ui-redesign/orchestrator` 等 6 個 ID |
| 目標頁可進入 | dev server 指令可用；需登入的頁面備妥 storageState 檔（gitignored 路徑） |
| （可選）命令檔已裝 | `Test-Path .opencode/commands/ui-redesign.md` 為 True |

## 2. 發起任務

**方式一（已裝命令檔）**：直接輸入 `/ui-redesign`：

```
素材：<PNG/JPEG 設計圖／HTML 原型路徑或網址／規格文件位置，可多行>
目標頁面：<頁面清單，如：登入頁（/login）>
特別要求：（可省略，如：保留既有表單驗證邏輯）
```

**方式二（未裝命令檔）**：把 primary agent 切換為 `ui-redesign/orchestrator` 後，下達同樣內容。

素材與目標頁面**缺一時 orchestrator 會反問你**，不會自行推測。

> **多頁批次**：建議一次任務只做一頁（每頁一份產物資料夾），完成後再開下一頁——批次過大會拉長視覺迴圈輪次。

## 3. 流程中會發生什麼（七階段 × 你的參與點）

```
階段 0 準備 → 1 基準建立 → 1.5 決策點 → 2 實作 → 3 視覺迴圈 → 4 驗收 → 5 交付
```

### 階段 0：準備

- orchestrator 讀 ui-profile（不存在會用範本問你逐欄補齊，**經你確認後才開工**）。
- **會問你**：是否使用 git worktree 隔離區（要／不要）。
  - 「要」：依 ui-profile「流程程序文件」或套件內建程序建立 `.worktrees/ui-<slug>`。
  - 「不要」：直接在主工作區進行。
- **會問你**（若 port 已占用）：沿用你手動開的 dev server，或由 orchestrator 另開 port。沿用時收尾不會動它。

### 階段 1：基準建立（兩個 agent 並行，你等待）

- `functional-qa` 盤點既有功能、補特徵測試、寫回歸腳本、記錄測試基準線。
- `design-analyzer` 解析素材產出設計規格、tokens、元件對照、待確認清單。
- **互動點**：`functional-qa` 寫入專案測試檔時會跳 **ask**——請核准（這是在織回歸防護網）。誤按拒絕時該項工作會停下並改列「建議手動回歸」，可之後再補。

### 階段 1.5：設計決策點（**你需要裁決**）

- orchestrator 把「靜態素材無法確認的設計決策」（hover／focus／載入中／RWD 斷點等）整理成清單問你。
- 你逐項裁決後，由 design-analyzer 把決策**寫回** pending-questions.md 並修訂規格。
- **會問你**：確認 `design-spec.md` 與 `design-tokens.json` 兩者——**確認後規格凍結**，進入實作；之後要改規格需再走一次確認。

### 階段 2：實作（你等待）

- `developer` 分批修改（先 tokens／共用元件 → 頁面分區），優先重用既有元件與邏輯。
- 碰到禁改區（API 契約／store／socket／路由資料流）時會**停手回報**，由你決定放行與否。

### 階段 3：視覺迴圈（每輪看圖判讀，最多 3 輪）

- `visual-qa` 每輪產出：`visual-report.md`＋該輪 `.artifacts/r<N>/` 的截圖／overlay／diff 圖。
- 你可隨時打開 overlay／diff 圖核對；**差異百分比是參考值（預設門檻 <2%），判讀以疊圖為準**。
- **第 3 輪仍未過時，會問你四選項**：
  1. 再修一輪（每次 +1 輪，不自動續跑）
  2. 裁決差異可接受（帶未解項進驗收，記入「剩餘限制」）
  3. 你自己手動調整（保留現狀，之後重跑比對）
  4. 暫停任務（worktree 位置與分支會保留）

### 階段 4：驗收（兩條線序列化，你等待＋看結果）

- 先 `functional-qa`：重跑回歸腳本＋全部測試＋build → `functional-report.md`（基準線項數不得少於、不得有失敗）。
- 後 `reviewer`：lint／測試／build＋需求符合度五步驟＋XSS/安全＋樣式污染＋非預期改動 → `code-review.md`。
- 任一 FAIL → 指定範圍退回 developer → 重跑對應驗收（驗收另有獨立的 3 輪預算）。
- 視覺退回後若動了樣式／template，orchestrator 會加跑一次快速視覺比對（不計輪）。

### 階段 5：交付（**你需要審核**）

- 彙整固定四項：三份報告結論、剩餘限制與待確認事項、修改檔案清單、建議手動回歸清單。
- **最終驗收由你裁決**：看完最終輪 overlay／diff 圖與 visual-report 後決定。
- **會問你**：繁體中文 commit 訊息審核——同意才 commit（含產物文件；在 worktree 內提交）。
- **會問你**：worktree 處理（合併並清除／保留／直接丟棄）。
- **絕不 push**——需要時你自行 `git push`。

## 4. 互動點總表（什麼時候會找你）

| 時機 | 形式 | 內容 |
|---|---|---|
| 開工前 | question | worktree 要不要；ui-profile 缺失時逐欄補齊 |
| 階段 0 | question | port 占用時：沿用或另開 |
| 階段 1 | ask | functional-qa 寫專案測試檔 |
| 階段 1.5 | question | 設計決策裁決；規格與 tokens 凍結確認 |
| 階段 3 | question | 3 輪 FAIL 後的四選項 |
| 階段 4 | （無） | 兩條線跑完你看報告 |
| 階段 5 | question | commit 訊息審核；worktree 處理 |
| 清除時 | ask | `worktree remove`、branch 刪除、merge、commit |

> 子 session 的 ask 應回到主對話供你點選；若看不到，回報 orchestrator。

## 5. 看懂產物

```
<產物根目錄>/<頁面slug>/
├── functional-baseline.md   功能基準：功能清單＋測試保護狀態＋基準線（測試項數）
├── design-spec.md           設計規格：區域→區塊→元件，每項含數值＋來源等級
├── design-tokens.json       具名 token（顏色、字級、間距、圓角…），含來源等級
├── component-mapping.md     新舊元件對照與復用方案
├── pending-questions.md     你的決策紀錄（事後可追溯為什麼這樣做）
├── visual-report.md         VERDICT＋ISSUES（嚴重度／位置／證據圖路徑）＋剩餘限制
├── functional-report.md     VERDICT＋與基準線對照（項數、失敗數）
├── code-review.md           VERDICT＋ISSUES＋需求符合度證據
├── scripts/                 客製回歸腳本（可累積成回歸資產，下次任務重用）
└── .artifacts/r<N>/         1440x900-actual.png（實際截圖）／-overlay.png（50/50 疊圖）／-diff.png（差異標色）
```

- **來源等級三級**：`可確認`（HTML 原型量測值）／`量測推估`（圖片目測，標信心度）／`需要設計決策`（已由你在決策點裁定）。**推估不等於確認**，驗收時可據此追問。
- **diff 圖怎麼看**：差異像素以醒目色標出；先看 `-overlay.png` 找「偏移／大小差」，再看 `-diff.png` 找「顏色／字級差」。
- `.artifacts/` 不進 git；文字產物與 `scripts/` 進版控（目標專案的 .gitignore 依安裝指南第 11 項設定）。

## 6. 常用操作

- **暫停任務**：任何階段可要求暫停；worktree、dev server、產物全部保留，orchestrator 會回報暫停位置（分支與 worktree 路徑）。
- **續跑**：目前版本**沒有**續跑專用命令——切回 `ui-redesign/orchestrator` 後描述「接續上次的 UI 重構任務」＋提供暫停時的分支／slug 即可，orchestrator 會先盤點現況再續。
- **單頁重驗**：請 orchestrator「重跑 `<slug>` 的視覺比對」即可（快速比對不計輪數）。
- **修改後重驗**：你手動調整了樣式後，請 orchestrator 重跑一次視覺比對確認。
- **手動清理殘留 worktree**：**不要直接 `git worktree remove --force`**——worktree 內可能有 node_modules 與 kit 的 junction，跟隨刪除會毀掉主工作區的 node_modules 與整個 kit。一律交給 orchestrator 依程序清除（先拆兩個 junction 再 remove），或參照 `worktree-procedures.md` 手動執行拆除順序。

## 7. 異常時怎麼辦

| 情況 | 處理 |
|---|---|
| dev server 啟動失敗 | orchestrator 停止並回報；你決定重試或中止（不會擅自跳過） |
| 沿用的 dev server | 收尾一律不終止，結束時會告知「沿用的 dev server 保留未動」 |
| 設計素材缺失／格式不符 | orchestrator 問你補件或裁決；agent 不推測、不虛構 |
| ask 被誤按拒絕 | 該項停止並回報；功能改列「建議手動回歸」，之後可重跑或手動補 |
| 工具用 Node 失效 | 停止並回報；依安裝指南第 7 項重跑 setup.cmd |
| 同一工具連續失敗 3 次 | 停止並回報你裁決 |
| 同一視覺問題連修 3 次無改善 | 提前停止，重新分析原因（可能要求重新量測），不盲目重試 |

## 8. 驗收標準速覽

| 線 | 門檻 |
|---|---|
| 視覺 | 差異像素百分比為**參考門檻**（預設 <2%，ui-profile 可調）；**最終由你看圖裁決** |
| 功能 | 回歸腳本全過＋全部測試項數**不少於基準線**＋零失敗＋build 成功 |
| 程式審核 | VERDICT PASS／FAIL＋嚴重度三級（嚴重／一般擋 PASS，建議不擋） |
| 交付 | commit 內含產物文件；push 由你執行；建議手動回歸清單由你人工確認 |

## 9. 常見問題

**Q：為什麼階段 1 要花那麼久？** 防護網先織好（特徵測試＋回歸腳本）是套件的核心設計——改版後的功能保障靠這段建立，時間花在刀口上。

**Q：可以跳過決策點直接實作嗎？** 不建議。pending-questions 的決策（hover／RWD 等）沒有裁決，developer 只能推估，視覺迴圈會多打好幾輪。

**Q：測試檔的 ask 每次都跳很煩？** 這是刻意設計（套件不知道你的測試慣例，由你逐次把關）。核准後該輪不再重複詢問同一檔案。

**Q：視覺達到門檻了，為什麼還問我驗收？** 差異百分比無法涵蓋「看起來對不對」（字體渲染、偽差異）；最終驗收永遠由人裁決，這是套件的鐵則。

**Q：push 是誰做？** 套件**絕不 push**，交付後由你自行 `git push`。
